# A Trustworthy Hybrid Question Answering Method for Heterogeneous FMEA Data Based on Query Intermediate Representation and Evidence Adjudication


## Abstract

Failure Mode and Effects Analysis (FMEA) is widely used to record potential failure modes, failure causes, failure effects, control measures, and risk evaluation indicators in products, processes, and systems. As project data accumulates, FMEA forms become an important source of engineering knowledge. However, tables from different sources often differ in field names, column structures, empty-value conventions, and risk indicator formats, which makes cross-table precise lookup, relation locating, and answer tracing inefficient. Large language models and retrieval-augmented generation provide a new way to access FMEA data through natural language, but generative answers may be unsupported, and vector retrieval is not stable enough for numerical fields and structured relations. To address these issues, this paper proposes a trustworthy hybrid question answering method for heterogeneous FMEA data based on Query Intermediate Representation and evidence adjudication. The method first builds a project-level unified schema according to FMEA industry standards and standardizes multi-source tables into stable fields. It then uses Query IR to explicitly represent question intent, target entities, risk indicators, constraints, and output types, and routes questions among CSV direct answering, deterministic rules, knowledge graph queries, and vector retrieval. Finally, an evidence adjudication mechanism checks evidence sufficiency, consistency, and traceability to avoid unsupported risk conclusions. Experiments on a standard DFMEA question answering set and a lithium iron phosphate battery FMECA question answering set show that the proposed method achieves high-accuracy traceable question answering under heterogeneous FMEA table conditions.

Keywords: FMEA; knowledge graph; retrieval-augmented generation; Query Intermediate Representation; evidence adjudication; trustworthy question answering

Chapter 1 Introduction

Modern industrial systems increasingly couple product structures, processes, control logic, and operating environments. A potential failure in a single component or process step may propagate through system links and lead to quality, safety, or economic risks. Engineers therefore need to continuously consult existing risk records and rapidly locate failure modes, causes, effects, control measures, and risk priorities during product development, process design, and operation maintenance.

Failure Mode and Effects Analysis (FMEA) is an important method for recording and organizing such risk information. It identifies potential failure modes around product functions, process steps, or system units, and records failure causes, failure effects, existing controls, and risk levels. Once FMEA forms have been created, their value is not limited to one-time review. They also support project reuse, problem tracing, and risk knowledge querying. In practice, however, FMEA data is usually stored in dispersed tables. Relations among failure modes, causes, effects, control measures, and risk indicators are embedded in rows and columns, so engineers still need manual filtering, comparison, and summarization. This limits fast and precise access to FMEA knowledge.

Large language models (LLMs) and Retrieval-Augmented Generation (RAG) provide a new technical path for FMEA table question answering. LLMs can understand natural language questions and return answers in a conversational form, while RAG retrieves relevant records from external data sources to reduce the dependence on parametric generation. In FMEA scenarios, these methods can lower the access barrier to tabular data and improve the retrieval efficiency of complex risk information. However, existing methods still have clear limitations. General-purpose generative models may produce unsupported conclusions, vector retrieval may fail to handle precise indicators such as S, O, D, and RPN reliably, and heterogeneous field definitions may reduce retrieval consistency across FMEA tables.

An FMEA question answering system therefore needs to address three connected problems. First, tables from different sources must be mapped into unified fields so that the same type of risk information has consistent semantics. Second, the system must select an appropriate answering route according to the question type, because numerical lookup, relation retrieval, conditional filtering, and semantic search require different data access mechanisms. Third, the system must check evidence sources, evidence consistency, and evidence sufficiency before returning answers, so that retrieved candidates or model inferences are not directly treated as reliable conclusions.

Query Intermediate Representation provides a key bridge for these problems. FMEA questions often contain slots such as failure modes, process scopes, risk indicators, relation types, and expected output forms. If raw natural language questions are directly passed to retrieval or generation modules, intent recognition and route selection may become unstable. Query IR parses a question into structured fields, including intent, entities, metrics, constraints, scope, and output type. It enables downstream modules to execute CSV lookup, rule-based answering, knowledge graph querying, or vector retrieval based on an explicit task description. It also decouples question understanding from query execution and provides inspectable query evidence for evidence adjudication.

Based on the above analysis, this paper proposes a trustworthy hybrid question answering method for heterogeneous FMEA data based on Query Intermediate Representation and evidence adjudication. The method first constructs a project-level unified schema according to FMEA industry standards and standardizes FMEA tables from different sources into a stable data representation. It then uses Query IR to organize natural language questions and selects among CSV direct answering, deterministic rules, knowledge graph queries, and vector retrieval through hybrid retrieval routing. Finally, it introduces an evidence adjudication mechanism to judge the sufficiency, consistency, and traceability of candidate evidence. The main contributions are as follows:

1. A project-level unified schema is constructed for heterogeneous FMEA tables, with governance fields such as source file, source row number, and dataset ID retained to support cross-table question answering and answer tracing.

2. A Query IR for FMEA questions is designed to transform natural language questions into structured representations containing intents, entities, metrics, constraints, and output types.

3. A hybrid retrieval route is built by combining deterministic table lookup, rule-based answering, knowledge graph querying, and vector retrieval into a layered question answering workflow.

4. An evidence adjudication mechanism is introduced to check evidence sufficiency, consistency, and source information before answer generation, reducing the impact of unsupported answers on engineering risk judgment.

The remainder of this paper is organized as follows. Chapter 2 reviews related work on FMEA, knowledge graphs, RAG, Query Intermediate Representation, and trustworthy question answering. Chapter 3 defines the FMEA data structure and problem formulation. Chapter 4 presents the proposed hybrid retrieval question answering method. Chapter 5 reports the experimental evaluation. Chapter 6 discusses current limitations. Chapter 7 concludes the paper and outlines future work.

Chapter 2 Related Work

This chapter reviews research on FMEA, knowledge graphs, large language models, and retrieval-augmented generation. FMEA is a systematic method in reliability engineering and risk management. It aims to identify potential failure modes before failures occur in products, processes, or systems, and to evaluate their effects, causes, controls, and risk levels. IEC 60812 defines FMEA/FMECA as an important technique for failure analysis and risk evaluation, emphasizing failure effect identification across system, subsystem, component, and process levels【IEC 60812: Failure modes and effects analysis (FMEA and FMECA)】. The AIAG & VDA FMEA Handbook specifies engineering procedures, table structures, and risk evaluation requirements for design FMEA and process FMEA【Failure Mode and Effects Analysis FMEA Handbook】. SAE J1739 further covers design FMEA, process FMEA, and machinery FMEA, providing detailed table specifications for different engineering objects【SAE J1739: Potential failure mode and effects analysis in design, manufacturing and assembly processes, and machinery】. These standards indicate that FMEA is not merely a record of failure items. It is also a structured representation of failure modes, causes, effects, controls, and risk indicators.

As engineering systems become more complex, FMEA data faces increasing challenges in information organization. MIL-STD-1629A decomposes FMECA into tasks such as failure mode, effects, and criticality analysis, reflecting the need to record and evaluate risk information in a systematic and hierarchical manner【MIL-STD-1629A: Procedures for performing a failure mode, effects and criticality analysis】. NASA GSFC-HDBK-8004 emphasizes that FMEA is continuously updated with design information, operating conditions, and engineering knowledge, indicating the long-term maintenance and reuse value of FMEA data【NASA GSFC-HDBK-8004: Performing a failure mode and effects analysis】. In practice, FMEA forms generated by different departments, projects, and tools often differ in field names, table structures, and filling conventions. These differences make it difficult to locate common risks, compare risk indicators, or reuse historical experience across multiple forms. Recent studies have explored ontologies, knowledge graphs, and artificial intelligence to improve FMEA knowledge organization and risk analysis. For example, improved DFMEA has been combined with a knowledge graph to represent associations among components, failure modes, and risk information in complex products【Combining improved DFMEA with knowledge graph for component risk analysis of complex products】. A survey on advanced systems engineering also shows that AI, NLP, and ontology technologies are increasingly used to support FMEA modeling, reuse, and analysis【AI- and Ontology-Based Enhancements to FMEA for Advanced Systems Engineering: Current Developments and Future Directions】. These studies suggest that FMEA information use is moving from table reading toward structured knowledge management.

Knowledge graphs provide a technical basis for structuring FMEA data. A knowledge graph represents facts through nodes, properties, and relations, making it suitable for modeling statements such as a failure mode occurs at a process step, is caused by a certain cause, or results in a certain effect【Knowledge Graphs】. Compared with tables, knowledge graphs make entity relations explicit and support conditional retrieval and relation traversal through graph query languages. Failure information fusion studies also show that knowledge graphs can integrate dispersed failure information and improve decision reliability【A Knowledge Graph-Based Failure Information Fusion Method for Improving Decision Reliability】. Existing FMEA-KG-RAG research maps FMEA tables into a knowledge graph and constructs vector representations on top of the graph structure to support both graph queries and semantic retrieval【Knowledge graph enhanced retrieval-augmented generation for failure mode and effects analysis】. These methods are important for FMEA question answering. However, graph queries usually require accurate schema knowledge, and complex natural language questions still require additional parsing and routing.

Large language models provide a new interface for FMEA data interaction. LLMs are effective in natural language understanding and generation, and can help users access FMEA forms, engineering documents, and domain knowledge through question answering. Existing work has applied LLMs to FMEA-assisted risk management for technical processes and products, showing their potential to reduce the interaction burden when engineers use complex risk documents【Enhance FMEA with Large Language Models for Assisted Risk Management in Technical Processes and Products】. However, FMEA question answering is a precision-sensitive engineering task. Answers often involve numerical values, causal relations, and control measures. Natural language generation models may produce hallucinated or unsupported statements in factual tasks, as discussed in hallucination surveys【Survey of Hallucination in Natural Language Generation】. LLMs can therefore support question understanding and answer expression, but should not generate FMEA risk conclusions without evidence constraints.

Retrieval-Augmented Generation mitigates the factual limitations of LLMs by retrieving external knowledge. Typical RAG methods store document chunks in a non-parametric store, retrieve relevant contexts for a given question, and use a language model to generate an answer【Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks】. In table processing, LLMs have been used for table question answering, table understanding, and complex data analysis. However, table structure, field semantics, and numerical relations remain key factors for reliability【Large language model for table processing: a survey】. For FMEA data, vector retrieval can improve semantic recall, but may lose the symbolic meaning and field ownership of numerical values. Risk indicators such as RPN, severity, occurrence, and detection must be accurately read or calculated, rather than inferred only from semantic similarity. GraphRAG studies show that graph structures can enhance entity-relation modeling and structured retrieval【Graph Retrieval-Augmented Generation: A Survey】. Trustworthy RAG research further highlights evidence sources, answer traceability, and conflict detection【Trustworthiness in Retrieval-Augmented Generation Systems: A Survey】. RAG hallucination detection also shows that retrieved contexts do not fully prevent evidence-inconsistent generation, making verification necessary between retrieval and answer output【ReDeEP: Detecting Hallucination in Retrieval-Augmented Generation via Mechanistic Interpretability】.

Natural language question answering over structured data usually transforms user questions into structured forms rather than executing the raw questions directly. Semantic parsing, Text-to-SQL, and intermediate representations are commonly used for this purpose. Text-to-SQL surveys identify question understanding, schema understanding, and query generation as key components of natural language database interfaces【A Survey of Text-to-SQL in the Era of LLMs: Where Are We, and Where Are We Going?】【Next-Generation Database Interfaces: A Survey of LLM-based Text-to-SQL】. Natural language interfaces for tabular data also require alignment between user questions, table fields, data types, and query targets【Natural Language Interfaces for Tabular Data Querying and Visualization: A Survey】. The Spider dataset highlights the importance of complex queries and cross-schema generalization in semantic parsing【Spider: A Large-Scale Human-Labeled Dataset for Complex and Cross-Domain Semantic Parsing and Text-to-SQL Task】. IRNet further shows that an intermediate representation can reduce the difficulty of directly mapping natural language to SQL and improve query generation controllability【Towards Complex Text-to-SQL in Cross-Domain Database with Intermediate Representation】. These studies motivate the use of Query IR in this paper. FMEA questions should first be parsed into intents, entities, metrics, constraints, and output types before being routed to CSV lookup, rule-based answering, graph querying, or vector retrieval.

Evidence adjudication is also required for trustworthy FMEA question answering. Retrieving external content does not guarantee that the final answer is supported by evidence. RAG fact-checking studies propose lightweight verifiers after generation to determine whether answers are grounded in retrieved contexts【Provenance: A Light-weight Fact-checker for Retrieval Augmented LLM Generation Output】. Answer attribution studies examine the correspondence between generated claims and evidence passages, emphasizing that trustworthy RAG should identify which evidence supports each conclusion【Model Internals-based Answer Attribution for Trustworthy Retrieval-Augmented Generation】. Citation reliability research further treats the relation between generated citations and supporting evidence as an explicit verification target【VeriCite: Towards Reliable Citations in Retrieval-Augmented Generation via Rigorous Verification】. Automated fact-checking studies show that conflicting retrieved evidence should not be resolved by directly selecting a single candidate; instead, the system should detect conflicts and make conservative decisions【Resolving Conflicting Evidence in Automated Fact-Checking: A Study on Retrieval-Augmented LLMs】. In FMEA question answering, these ideas can be translated into adjudication over structured fields, graph relations, and vector candidate evidence, determining whether the evidence is sufficient, consistent, and capable of supporting the final answer.

In summary, existing studies provide useful foundations for FMEA standardization, knowledge graph modeling, LLM-assisted analysis, RAG-enhanced retrieval, structured query parsing, and evidence verification. However, three limitations remain. First, field naming, empty-value rules, and template structures in heterogeneous FMEA forms have not been sufficiently unified. Second, FMEA question answering combines numerical lookup, relation retrieval, conditional filtering, and semantic search, making a single route insufficient for both accuracy and generalization. Third, engineering risk scenarios require explicit Query Intermediate Representation, evidence tracing, and conflict adjudication. Based on these limitations, this paper constructs a project-level unified schema, introduces Query IR to organize natural language questions, and improves heterogeneous FMEA question answering through hybrid retrieval routing and evidence adjudication.

Chapter 3 FMEA Data and Problem Definition

3.1 FMEA-Related Industry Standards

FMEA and its extended form FMECA have been standardized in multiple engineering domains. Their common goal is to identify and record potential failure modes, failure effects, failure causes, existing control measures, and risk priorities before product or process risks become actual failures. IEC 60812 defines FMEA/FMECA as a reliability and risk analysis technique, emphasizing the analysis of potential failure effects on functions, safety, missions, and maintenance activities across system, subsystem, component, and process levels. MIL-STD-1629A further decomposes FMECA into failure mode and effects analysis and criticality analysis, requiring standardized tables for failure modes, local effects, higher-level effects, final effects, severity levels, detection methods, and compensating measures. NASA GSFC-HDBK-8004 follows this engineering tradition and treats FMECA as a dynamic risk assessment document updated with design, material, operational, and mission knowledge. This indicates that FMEA data is not only a one-time analysis result, but also an engineering knowledge carrier for risk closed-loop management and knowledge reuse.

In practice, different domains develop FMEA templates according to product types, process characteristics, and risk evaluation requirements. Standards such as the AIAG & VDA FMEA Handbook and SAE J1739 define field structures, analysis procedures, and risk evaluation methods for common forms such as DFMEA and PFMEA. These standards usually analyze fields including item or function, potential failure mode, potential failure effect, severity, potential failure cause, occurrence, current prevention control, current detection control, detection, risk priority number, and action priority. Although industry standards differ in rating scales, table formats, and terminology, their core semantics are stable. They organize risk knowledge around the chain of function or process step, failure mode, failure effect, failure cause, control measure, and risk indicator. The data definition and unified schema in this paper are built on this common structure. They retain core FMEA business fields to express failure chains and risk evaluation logic, while adding governance fields such as data source, project ID, dataset ID, source file, and source row number so that heterogeneous tables remain traceable and verifiable after entering the question answering system.

3.2 Structured Problem Definition

This section gives a set-theoretic definition of the FMEA problem【Knowledge graph enhanced retrieval-augmented generation for failure mode and effects analysis】. Let the original FMEA data be \(D=\{T_1,T_2,\ldots,T_n\}\), where each table \(T_i\) is represented by a column set \(H_i\) and a row set \(R_i\). Since tables differ in field names, filling conventions, and empty-value rules, the system first constructs a standardization mapping \(\phi_i:T_i\rightarrow X_i\), which converts the original table into structured data \(X_i\) under the project-level unified schema. In this schema, each valid record \(x\in X_i\) contains at least a process or function item \(p\), a failure mode \(f\), a failure effect \(e\), a failure cause \(c\), a control measure \(m\), and risk indicators \(s,o,d,rpn\). Here, \(s\), \(o\), and \(d\) denote severity, occurrence, and detection, while \(rpn\) denotes the risk priority result.

The core FMEA semantics can then be represented by mappings. Let \(F=\{f_1,f_2,\ldots,f_k\}\) be the set of failure modes, \(P\) the set of process or function items, \(E\) the set of failure effects, \(C\) the set of failure causes, and \(M\) the set of control measures. For any failure mode \(f\in F\), the following mappings are defined:

- Location mapping \(A:F\rightarrow P\), which maps a failure mode to its corresponding process step or functional object;

- Effect mapping \(E_f:F\rightarrow E\), which maps a failure mode to its possible effects;

- Cause mapping \(C_f:F\rightarrow C\), which maps a failure mode to its potential causes;

- Control mapping \(M_f:F\rightarrow M\), which maps a failure mode to prevention controls, detection controls, or recommended actions.

Risk evaluation is represented as \(S:E\rightarrow \Omega_s\), \(O:C\rightarrow \Omega_o\), and \(D:M\rightarrow \Omega_d\), where \(\Omega_s\), \(\Omega_o\), and \(\Omega_d\) denote the rating domains specified by a given FMEA or enterprise standard. For \(f\in F\), the risk priority number is defined as \(RPN(f)=S(E_f(f))\times O(C_f(f))\times D(M_f(f))\). If the original table provides an RPN value, the system prioritizes the recorded value. If RPN is missing and \(S\), \(O\), and \(D\) are available, the formula is used to compute it.

To support relation queries and evidence tracing, standardized FMEA data can be constructed as a knowledge graph \(G=(V,\mathcal{R},T,L)\). \(V\) denotes the node set, including FailureMode, ProcessStep, FailureEffect, and FailureCause. \(\mathcal{R}\) denotes the relation set, including occursAtProcessStep, resultsInFailureEffect, and isDueToFailureCause. \(T\) denotes factual triples composed of a head node, a relation, and a tail node. \(L\) denotes textual, numerical, and source attributes attached to nodes or relations. Thus, an FMEA row is no longer an isolated collection of cells, but a local risk subgraph centered on a failure mode.

At the question answering level, a user question is denoted as \(q\), and the system output is denoted as \(Y=(a,E_v,ir,\rho,\sigma)\). \(a\) is the answer text, \(E_v\) is the evidence set, \(ir\) is the Query Intermediate Representation, \(\rho\) is the route, and \(\sigma\) is the evidence adjudication state. Query IR describes question intent, target entities, risk indicators, constraints, query scope, and output type. The route selects among CSV direct answering, rule-based answering, graph query, and vector retrieval. The evidence adjudication state determines whether the evidence is sufficient, consistent, and able to support the final answer. The target problem can therefore be defined as follows: given heterogeneous FMEA data \(D\), construct a unified representation \(X\) and a graph structure \(G\), and generate for any user question \(q\) an answer \(Y\) with explicit evidence sources, a structured explanation path, and a trustworthiness state label.

Chapter 4 Hybrid Retrieval Question Answering Method for FMEA (Core Research Content)

4.1 Overall Method Framework

The proposed method is designed for trustworthy question answering over heterogeneous FMEA tables. As shown in the overall framework, the system consists of four main modules: data standardization, knowledge graph construction, hybrid retrieval routing, and evidence adjudication. These modules form a closed pipeline from source table ingestion to traceable answer generation.

The data standardization module maps heterogeneous FMEA tables to a project-level unified schema. It resolves differences in field names, column structures, empty-value conventions, and risk indicator formats, and it retains source attributes for later evidence tracing.

The knowledge construction module builds an FMEA knowledge graph from the standardized records. Each valid record is represented as a local risk subgraph centered on a FailureMode node, and graph-neighborhood text chunks are embedded to support semantic retrieval.

The online question answering module first applies CSV-based direct lookup and deterministic rules for objective FMEA queries. If these paths are insufficient, the system constructs a Query IR to describe the intent, entities, metrics, constraints, and output type of the question, and then routes the query to structured graph retrieval or vector retrieval.

The evidence adjudication module checks whether the retrieved evidence is sufficient, consistent, and traceable. The system returns a confirmed answer only when the evidence can support the claim; otherwise, it reports missing information, conflicts, or pending candidate evidence.

The final output includes the answer text, readable context, raw evidence, Query IR, routing information, missing slots, and adjudication status. Therefore, the overall framework emphasizes deterministic evidence before generative responses and uses explicit evidence control to improve the reliability of FMEA question answering.

4.2 FMEA Data Standardization and Unified Representation

The first step of the proposed method is to convert heterogeneous FMEA tables into a unified data representation. This step is based on the FMEA industry standard table used in this project. The standard table defines 18 source fields: FMEA ID, product, analysis level, item or function, potential failure mode, potential failure effect, severity, potential failure cause or mechanism, occurrence, current prevention control, current detection control, detection, risk priority number, action priority, recommended action, action status, action result, and remarks. These fields cover the main information required for FMEA record interpretation, including the analyzed object, the failure chain, the risk evaluation values, and the follow-up action information.

The industry standard fields are not directly used as the internal data contract of the question answering system. They describe the expected input format of a standard FMEA table, whereas the project-level schema defines the stable representation used by normalization, graph construction, deterministic rules, Query IR execution, and evidence adjudication. Therefore, the standardization process maps source headers into English schema fields with explicit semantics and data types. For example, the source field "项目/功能" is mapped to ProcessStep, "潜在失效模式" is mapped to FailureMode, "潜在失效后果" is mapped to FailureEffect, and "潜在失效原因/机理" is mapped to FailureCause. The risk evaluation fields "严酷度(S)", "发生度(O)", "可探测度(D)", and "风险优先数(RPN)" are mapped to S, O, D, and RPN, respectively.

The main mapping from the industry standard table to the project-level schema is summarized as follows:

The project-level schema further adds governance fields that are not present in the industry standard table. These fields include Domain, DatasetID, ProjectID, SchemaVersion, SourceFile, SourceRowNo, and ImportBatchID. They do not describe the failure mechanism itself, but they are necessary for dataset management and answer traceability. SourceFile and SourceRowNo allow the system to trace an answer back to its original table and row. DatasetID and ProjectID distinguish different imported datasets and projects. SchemaVersion records the version of the normalization contract. This separation between business fields and governance fields is important for heterogeneous FMEA question answering, because the system must preserve both the engineering semantics and the evidence source.

During normalization, the system first strips redundant spaces from source column names and applies a column synonym dictionary. This dictionary handles field variants that appear in different FMEA reports. For example, "设计项目", "过程步骤", and "工序" can be normalized to ProcessStep; "严重度" and "严酷度(S)" can be normalized to S; "探测度", "探测度数", and "可探测度(D)" can be normalized to D. This rule-based normalization is deliberately domain-specific. It does not attempt to solve general natural language synonymy, but focuses on the column variants required by FMEA table ingestion.

After column mapping, the system standardizes cell values. Text fields are stripped and empty strings are converted to null values. Numerical fields, including S, O, D, and RPN, are converted to numeric values when possible. If the source table omits repeated process or function names because of merged-cell formatting, ProcessStep values are forward-filled to preserve the row-level semantics. If RPN is not available but S, O, and D are all present, the system computes RPN as the product of S, O, and D. If the source table already provides an RPN value, the recorded value is retained as the primary evidence. This rule avoids overwriting source evidence while still allowing risk priority recovery when the original table is incomplete.

The normalized output provides a stable input for all subsequent modules. The graph construction module uses ProcessStep, FailureMode, FailureEffect, and FailureCause to create nodes and relations. Deterministic question answering rules use FailureMode, FailureCause, FailureEffect, PreventControl, DetectionMeasure, RecommendedAction, and S/O/D/RPN for direct lookup and analytical queries. Query IR execution relies on the same schema to bind question entities, metrics, constraints, and output types to executable retrieval paths. Evidence adjudication uses the normalized fields and governance attributes to verify whether an answer is supported by consistent source evidence. In this way, FMEA data standardization is not only a preprocessing step, but also the data contract that connects heterogeneous source tables with trustworthy hybrid question answering.

4.3 FMEA Knowledge Graph Construction Method

After the heterogeneous FMEA tables are normalized into the project-level schema, the system further constructs a knowledge graph to represent the relational structure of risk knowledge. The purpose of this graph is not to generate new FMEA records, but to organize existing FMEA evidence in a form that supports relation traversal, multi-hop retrieval, and source-aware question answering. Compared with a flat table, the graph representation makes the links among process steps, failure modes, failure effects, failure causes, risk values, and control measures explicit.

The graph construction process takes the normalized CSV file as input. Before graph insertion, the system checks whether the required fields FailureMode and ProcessStep exist. Records without a valid failure mode or process step are skipped, because they cannot form a meaningful risk unit. If the RPN field is absent but S, O, and D are available, the system calculates RPN as the product of the three indicators. If RPN already exists in the source table, the original value is retained. This rule keeps the graph consistent with the evidence policy defined in the normalization stage.

For each valid FMEA record, the system creates a local risk subgraph centered on the FailureMode node. The ProcessStep node represents the item, function, process step, or operation to which the failure mode belongs. The FailureEffect node represents the consequence caused by the failure mode. The FailureCause node represents the potential cause or mechanism of the failure mode. The graph uses three main relations to connect these nodes: occursAtProcessStep links a failure mode to its process step, resultsInFailureEffect links a failure mode to its effect, and isDueToFailureCause links a failure mode to its cause.

The attribute design follows the project-level schema. The FailureMode node stores the central description of the failure mode together with S, O, D, RPN, prevention control, detection measure, recommended action, action priority, action status, action result, remarks, and source governance attributes. The ProcessStep node stores the process or functional object and related dataset attributes. The FailureEffect node stores the effect description and the associated severity value. The FailureCause node stores the cause description and the associated occurrence value. This design keeps the most frequently queried information close to the central failure mode, while preserving explicit semantic relations for graph traversal.

The graph insertion procedure uses merge semantics rather than unconditional creation. Therefore, repeated process steps, effects, causes, or failure modes can be reused when their identifying properties are the same. This reduces duplicate nodes and allows multiple records to share common risk concepts. At the same time, source-related attributes such as SourceFile, SourceRowNo, DatasetID, ProjectID, SchemaVersion, and ImportBatchID are preserved on the FailureMode node. These attributes allow an answer to be traced back to the imported table and the corresponding row.

After symbolic graph construction, the system builds vector-searchable evidence chunks. For each FailureMode node, the system traverses its neighboring ProcessStep, FailureEffect, and FailureCause nodes. It then converts the local subgraph into a textual chunk that contains ProcessStep, FailureMode, RPN, FailureEffect, S, FailureCause, O, prevention control, detection measure, recommended action, and D. The chunk is embedded by the Ollama embedding model and stored as a Chunk node. The Chunk node also records the element identifiers of the related FailureMode, FailureEffect, FailureCause, and ProcessStep nodes.

The FailureMode node is connected to the corresponding Chunk node through the isIndexed relation. This relation binds symbolic graph evidence and vector evidence together. When the user question can be answered by explicit graph relations, the system can use structured traversal. When the question is semantically vague or does not match deterministic rules, the system can retrieve candidate chunks through vector similarity. Because each chunk still stores links to graph nodes, vector retrieval results are not isolated text fragments; they remain connected to the structured FMEA evidence.

In this way, the graph construction method produces a hybrid knowledge layer. The symbolic part supports deterministic relation queries and multi-hop evidence chains, while the vector part supports semantic candidate retrieval. Both parts are derived from the same normalized schema and retain source attributes. Therefore, the constructed graph provides a unified evidence base for subsequent Query IR execution, retrieval routing, and evidence adjudication.
